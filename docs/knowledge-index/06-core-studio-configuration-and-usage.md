# Core + Studio Configuration and Usage (POC)

## Purpose

This guide documents the current Core and Studio application slice as it exists today: configuration model, runtime behavior, and operator usage.

It intentionally avoids deployment/install instructions and focuses on how this slice is expected to behave once available.

## What This Slice Covers

- auth, session, and org context switching behavior
- Studio configuration surfaces for org/user/persona/governance controls
- realtime setup flows for persona and room selection
- knowledge governance/document flows currently wired in Studio

## Configuration Contract (Current)

- Core is the backend policy and identity authority.
- Studio is the control-plane frontend for operators/admins.
- Configuration is tenant-aware and org-scoped.
- Session credentials are token-based and context-sensitive.

## Key Runtime Environment Values

- `VITE_KAIROS_CORE_API_BASE_URL`: Core API base URL override.
- `VITE_KAIROS_TENANT_ID`: tenant scope fallback used by frontend calls.
- `VITE_KAIROS_ORG_ID`: default org scope used by some pages until context is switched.

## Session and Auth Usage

Current auth flow used by Studio:

1. `POST /v1/auth/login`
2. `GET /v1/auth/me` (uses `org_options` to populate context choices)
3. `POST /v1/auth/context/switch` for org change

Token handling behavior:

- access + refresh tokens are persisted in local session storage keys
- if an API call returns `401` (non-auth endpoints), client attempts `POST /v1/auth/refresh`
- original request is retried once after successful refresh
- refresh failure clears session and requires user re-authentication

## Governance and Access Usage

Governance endpoints currently aligned in Studio:

- `GET /v1/studio/governance/baseline`
- `GET /v1/studio/settings`
- `PATCH /v1/studio/settings`
- `GET /v1/studio/app-access-grants`
- `POST /v1/studio/app-access-grants`
- `POST /v1/context/explain` (admin diagnostics)
- `POST /v1/policy/decision` (preflight decision checks)

Current usage expectations:

- deny-by-default app access grants
- generic deny messaging for users
- explain/debug payload detail available for admin/operator views

## Persona and Runtime Usage

Persona flows in this slice:

- primary route is `/create/persona`
- legacy reference route remains available as `/create/persona-ab`
- persona payloads include runtime provider/model selectors
- version history + rollback are surfaced through Studio persona APIs

Current usage expectations:

- provider/model options are loaded from system endpoints
- persona creation/update must remain contract-strict (OpenAPI fields only)
- rollback workflows are operator-facing and intentionally explicit

## Realtime Usage

Realtime setup in this slice focuses on room/persona wiring without changing chat payload contract behavior.

Current behavior:

- personas are loaded from configured realtime/studio persona sources with fallback
- rooms are loaded from configured room/channel sources with fallback
- websocket URL is generated by shared ws client utilities
- chat send payload flow is intentionally unchanged while validating backend compatibility

## Knowledge Usage

Knowledge page is now positioned as the document governance surface.

Current coverage:

- document list by org
- upload request surface (`/v1/knowledge/documents/upload`)
- visibility scope selection
- policy preflight (`/v1/policy/decision`)
- context explain diagnostics (`/v1/context/explain`)

## Known Caveats (POC)

- endpoint envelopes and item shapes are still converging across some services
- some admin UX is scaffolded and will be expanded (especially grant matrix depth)
- realtime setup is functional for room/persona wiring, but event tooling will continue to improve
- knowledge ingestion lifecycle detail is still being hardened

## Operator Checklist

- verify org context before applying governance/persona settings
- keep deny-by-default posture for new app grants
- run policy decision checks before changing visibility/upload defaults
- use explain diagnostics only in trusted admin contexts
